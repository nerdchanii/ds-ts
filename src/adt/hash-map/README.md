# 해시 맵 (HashMap)

키로 값을 평균 O(1)에 찾는 자료구조. 이 구현은 **분리 연결법(체이닝)** 을 쓰며 내장 `Map`/`Object`를 쓰지 않는다.

## 1. 추상 자료형(ADT) 정의

`HashMap<K, V>`는 서로 다른 키 K를 값 V에 대응시키는 사전(dictionary)이다. 키의 동일성은 `equals`로 판단하고, 같은 키는 최대 한 번만 존재한다(불변식). `hash`와 `equals`는 **같은 키면 같은 해시**라는 규약을 지켜야 한다.

| 연산 | 사전 조건 | 사후 조건 |
|---|---|---|
| `set(k, v)` | 키의 hash가 계산 가능 | `get(k) = v`. 새 키면 size+1, 기존 키면 값만 교체(size 불변) |
| `get(k)` | 없음 | 키가 있으면 값, 없으면 `undefined`. 맵은 변하지 않음 |
| `has(k)` | 없음 | 키 존재 여부. 값이 `undefined`여도 키가 있으면 `true` |
| `delete(k)` | 없음 | 있었으면 제거 후 `true`(size-1), 없으면 `false`(변화 없음) |
| `size` | 없음 | 저장된 항목 수 (0 이상) |
| `isEmpty()` | 없음 | `size === 0` |
| `clear()` | 없음 | 모든 항목 제거, `size = 0` |
| `keys()/values()/entries()/[Symbol.iterator]` | 순회 중 맵을 수정하지 않음 | 모든 항목을 정확히 한 번씩 방문. **순서는 보장 안 됨** |

## 2. 왜 쓰는가

- 배열은 인덱스로만 O(1) 접근이 되지만, 해시 맵은 "문자열/임의의 키"로 O(1) 접근을 준다.
- 실제 사용 예: 단어 빈도 세기, 캐시(메모이제이션), 중복 검사, 그룹핑(`groupBy`), 두 수의 합 문제, DB 인덱스·세션 저장소, 컴파일러 심볼 테이블.
- 핵심 아이디어: 키를 **해시 함수**로 정수로 바꾸고 `정수 % 버킷 수`로 배열 칸(버킷)을 바로 찾는다.

## 3. 구현 방식

```
buckets: [0] -> (a,1) -> (e,5)     <- 충돌한 키는 연결 리스트로 이어 붙임
         [1] -> null
         [2] -> (b,2)
         ...
```

- **버킷 배열 + 연결 노드**: 각 버킷은 `Node(key, value, next)` 체인의 머리. 삽입은 체인 머리에 붙여 O(1)(단, 같은 키 존재 여부를 먼저 체인 전체를 훑어 확인).
- **해시 함수**: 문자열은 djb2(`h = h*33 ^ c`), 숫자는 정수를 32비트로 쪼개 murmur3식 비트 혼합, 불린은 1231/1237. 소수·NaN·Infinity는 문자열로 바꿔 djb2. 그 외 타입(객체 등)은 `TypeError`이므로 생성자에 `hash`/`equals`를 주입한다.
- **인덱스 계산**: `(hash >>> 0) % capacity`. 커스텀 해시가 음수·소수를 돌려줘도 안전하다.
- **리해싱**: `size / capacity > 0.75`가 되면 버킷을 2배로 늘리고 모든 노드를 새 인덱스로 재배치한다(노드 재사용). 인덱스가 `capacity`에 의존하므로 재배치가 필수다.

### 충돌과 체이닝 vs 오픈 어드레싱

**충돌**: 서로 다른 키가 같은 버킷에 떨어지는 일. 버킷 수보다 키가 많으면(비둘기집 원리) 반드시 생긴다.

| | 체이닝 (이 구현) | 오픈 어드레싱 |
|---|---|---|
| 충돌 해결 | 버킷 안에 리스트로 연결 | 배열의 다른 빈 칸을 탐사(선형/이차/이중 해싱) |
| 부하율 | 1을 넘어도 동작(체인이 길어질 뿐) | 반드시 1 미만, 보통 0.5~0.7 이하 유지 |
| 삭제 | 노드 연결만 끊으면 됨 | 묘비(tombstone) 처리 필요 |
| 메모리/캐시 | 노드 포인터 오버헤드, 캐시 비친화적 | 연속 배열이라 캐시 친화적 |
| 클러스터링 | 없음 | 선형 탐사에서 1차 군집 발생 |
| 구현 난이도 | 쉬움 | 삭제·리사이즈가 까다로움 |

### 부하율(load factor)과 리해싱

부하율 α = 항목 수 / 버킷 수. 체이닝에서 한 체인의 평균 길이가 α이므로 탐색 평균 비용은 O(1+α). α를 0.75 이하로 묶으면 평균 O(1)이 유지된다. 용량을 2배씩 키우면 리해싱 O(n) 비용이 n번의 삽입에 걸쳐 분산되어 **분할 상환 O(1)** 이 된다.

## 4. 시간·공간 복잡도

n = 항목 수. 평균은 해시가 고르게 퍼진다는 가정.

| 연산 | 평균 | 최악 (전부 충돌) | 비고 |
|---|---|---|---|
| `set` | O(1) 분할 상환 | O(n) | 체인 탐색 + 가끔 리해싱 O(n) |
| `get` / `has` | O(1) | O(n) | 체인 길이에 비례 |
| `delete` | O(1) | O(n) | 체인 탐색 |
| `size` / `isEmpty` | O(1) | O(1) | 카운터 유지 |
| `clear` | O(초기 용량) | 동일 | 버킷 배열 새로 할당 |
| `keys/values/entries` 순회 | O(버킷 수 + n) | 동일 | 빈 버킷도 훑음 |
| 리해싱 | O(n) | O(n) | 노드 재사용 |
| 공간 | O(n + 버킷 수) | 동일 | 항목당 노드 1개 |

최악은 해시가 한 값으로 몰리는 경우(테스트의 `hash: () => 42`)로, 맵이 연결 리스트로 퇴화한다.

## 5. TypeScript로 구현할 때의 장단점·주의점

### JS의 Map / Object와의 차이

| | 이 HashMap | `Map` | `Object` |
|---|---|---|---|
| 키 타입 | 해시/equals를 주입하면 무엇이든 (기본은 string/number/boolean) | 무엇이든, 비교는 SameValueZero(객체는 참조 비교) | 문자열·심볼만 (숫자는 문자열로 변환) |
| 순서 | 버킷 순서(삽입 순서 아님) | **삽입 순서 보장** | 정수형 키가 먼저 오름차순, 나머지는 삽입 순 |
| 객체 키 값 비교 | `equals`로 값 비교 가능 | 불가(참조만) | 불가 |
| 프로토타입 오염 | 없음 | 없음 | `__proto__`, `toString` 등 주의 |
| 성능 | 엔진 내장 대비 느림(학습용) | 네이티브 최적화 | 모양(hidden class) 최적화 |

### 장점
- 제네릭 `HashMap<K, V>`로 키·값 타입을 컴파일 시점에 검사한다.
- `Iterable`을 구현해 `for...of`, 전개 연산자를 쓸 수 있다.
- 값 기반 동등성(예: 좌표 `{x, y}`)을 `hash`/`equals`로 정의할 수 있다.

### 주의점
- **hash와 equals의 일관성**: `equals(a,b)`가 참이면 `hash(a) === hash(b)`여야 한다. 어기면 키를 찾지 못한다.
- **키를 변경하지 말 것**: 키로 쓴 객체의 필드가 바뀌면 해시가 달라져 항목이 "사라진다".
- **`undefined` 값**: `get`만으로는 "없음"과 구분되지 않으므로 존재 확인은 `has`를 쓴다.
- **숫자 처리**: JS 숫자는 모두 64비트 실수다. `0`과 `-0`은 같은 키, `NaN`은 자기 자신과 같은 키로 취급한다(`===`가 아니라 `Map`과 같은 방식). 비트 연산은 32비트로 잘리므로 큰 정수는 상·하위로 나눠 섞는다.
- **`%` 와 음수**: JS의 `%`는 음수 결과가 나올 수 있어 `>>> 0`으로 부호 없는 정수로 바꾼 뒤 사용한다.
- **순회 중 수정 금지**: 리해싱이 일어나면 순회 결과가 깨진다.
- **서비스 코드에서는** 내장 `Map`을 쓰는 것이 낫다. 이 구현은 원리를 이해하기 위한 교육용이다.
